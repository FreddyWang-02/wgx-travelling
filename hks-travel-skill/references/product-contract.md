# 五模块产品交付契约

## 固定产品形态

最终网页必须复用 `assets/frontend-template/`，并保留以下五个一级模块：

1. 概览：旅行摘要首页，继承原「出行」的交通与住宿能力（票面、分段、时间节点、票据、附件、编辑与清空）。
2. 行程：逐日列表、地点顺序与地图或绘图式路线。
3. 准备：预约、订票、复查和携带物品。
4. 记账：付款人、参与人、分摊、个人汇总与结算建议。
5. 资料：地点、票据、攻略、链接、来源和可选附件。

长篇攻略正文、表格报告或自制单页只能作为补充材料，不能替代五模块网页。

## 信息架构边界（Phase 3 冻结）

一级导航**始终为 5 项**：概览 / 行程 / 准备 / 记账 / 资料。详细交互骨架见 [产品 UX 架构 v1](product-ux-v1.md)。

- **地图不是一级模块**：它是「行程」模块内部的第二种视图（行程 / 地图 视图切换），继续承担路线总览与节点点选。
- **AI Copilot 不是一级模块**：它是全局能力（Floating Action Button + Bottom Sheet / Drawer），请求与 fallback 契约见 [Agent Bridge](agent-bridge.md)。
- 新增能力通过模块内入口或全局能力实现，禁止通过增加一级 Tab 实现，产品不得演变成七个底部 Tab。
- 「概览」是原「出行」的升级而非替代：改名后交通、住宿、票据与编辑能力必须原样保留。

## UI 选择门

正式部署前必须用本次旅行数据展示三种 UI：

- `aviation`：航空票夹，沿用既有原型设计。
- `natural`：自然手账。
- `minimal`：极简导览。
- `storybook`：晴日手账（Sunny Travel Storybook）。Phase 4A 新增，当前默认方向；首页版式见仓库根目录 `DESIGN.md`。选择它**不替换**其它六套风格的版式，只是新增一个可选方向。

用户确认后把选择写入顶层 `appearance.styleId`。明暗模式属于浏览器显示偏好。用户未确认样式时只允许生成标记为“UI 样式预览”的临时页面。

六种 UI 风格都必须为全局页面提供独立的深色主题变量，至少覆盖页面背景、卡片、导航、正文、次要文字、边框、按钮、输入框、弹窗和阴影。深色切换验收必须逐一检查五模块，地图单独变暗不得视为全局深色通过。

V4 增加三个先行审核方向：

- `collage`：拼贴裁纸风。
- `print`：印刷风。
- `urban`：都市设计风。

三者先以出行模块完成视觉审核。用户确认某一方向后，再把该方向扩展到其余四个模块。生成预览不得自动视为用户已经选择。

## V4 交互与缺省契约

### 航空票夹视觉基线

- `aviation` 必须直接沿用 `travel-prototype` 的航空票夹构图：航空蓝顶部、目的地代码背景、紧凑五模块导航、纵向航程轨道、突出登机口、票面穿孔与双列票面字段。
- 出行模块采用“主票面 + 右侧关键时间与备注”的桌面布局；移动端按票面、关键时间、备注顺序单列排列。
- 行程日期与节点沿用原型的紧凑信息层级：日期按钮清晰、节点使用轻边框卡片、编号与时间保持强识别。
- 新功能优先嵌入现有原型结构。禁止仅保留配色、圆角和“票夹”名称后另建通用卡片版式。
- 视觉验收至少包含航空票夹桌面、航空票夹移动端和行程移动端三张截图，并与原型核对顶部比例、票面构图、导航位置和信息密度。

- 卡片、大容器、弹窗、输入框和按钮使用统一圆角层级；移动端 390px 宽度不得出现页面级横向溢出。
- 所有新增与编辑弹窗在视口内水平、垂直居中。移动端使用安全边距内的近全宽弹窗：表单单列、输入控件至少 48px、正文输入字号至少 16px、保存区吸附底部；桌面端使用居中双列表单。
- 顶栏只保留品牌、样式、更多和主题入口。导出、附件、分享和数据操作收进“更多”。
- 五个模块分别提供模块内新增入口：添加交通、添加行程、添加地点、添加住宿、新增待办、记一笔、新增资料和上传附件。禁止使用统一“维护旅行”多 Tab 弹窗替代这些入口。
- 点击五模块一级 Tab 后，将对应模块标题滚动到视口起始位置；移动端底部导航不得把标题遮住。
- 模块标题需要操作按钮时使用统一标题操作区。桌面与移动端保持标题、历史和新增入口同行；360px 以下允许“历史”退化为图标、“新增出行”缩写为“新增”，不得让操作区独占下一行。
- 新增和编辑弹窗只展示当前记录的表单与保存、取消操作。现有记录列表留在对应模块页面；编辑和删除入口直接放在模块列表的记录上。
- 待办完成后标题和说明显示删除线；取消完成后恢复。保存失败保持原状态并允许重试。
- 移动端统计卡片优先三列并排；字段、按钮和辅助文案使用短标签与两行截断。
- “准备”的待完成、已完成、下一项统计始终使用同一组三列横排容器；桌面与移动端都不得退化为三个纵向散落字段。
- 地图加载超时、瓦片报错或瓦片只返回纯色占位内容时立即切换为绘图式路线图，并明确标注“路线示意”。
- 地图按坐标检索、路线数据、网页底图三个阶段协商能力。Agent 地图 MCP 或连接器优先完成地点与路线核验，网页优先接入宿主地图 SDK；OpenStreetMap 只作为最终底图保底。
- 行程默认先展示原型绘制地图，绘制地图包含路线、编号标记和选中地点详情卡；用户主动切换“网页底图”后再加载宿主 SDK 或 OpenStreetMap 保底。
- 绘制地图优先按 WGS84 经纬度归一化展示地点相对关系；无坐标节点按行程顺序使用中性网格布局。坐标或标签接近时执行简单避让，编号触控范围至少 44px，禁止循环复用固定少量坐标或写死与目的地无关的地标装饰。
- 网页底图必须来自官方文档明确开放且已完成授权配置的 SDK、API 或瓦片服务。禁止使用未文档化的裸瓦片端点，禁止以 HTTP 200、图片体积或 Referer 请求成功替代授权判断。
- 无来源的值显示 `—` 或零数据状态。禁止虚构账单、价格、班次、座位、登机口、住宿和付款人。
- 已完成状态只允许来自用户明确确认、用户网页操作或可信原始数据；攻略推荐默认使用计划中或待完成。
- 零数据集合保留空数组，页面显示对应空状态，禁止生成示例记录填充界面。
- 行程中的每个地点节点都提供拖拽手柄；桌面鼠标和移动端触摸均可调整同日顺序或跨日移动。列表、地图编号、连线与绘图式路线图必须读取同一份 `itineraryItems` 排序结果，拖拽保存后共同更新。
- 拖动仅由专用把手启动；鼠标与触摸统一走 Pointer Events。桌面鼠标使用 4px 移动阈值，触摸使用 7px 移动阈值；两端都关闭文字选择、提供前后插入反馈和边缘自动滚动。禁止只依赖兼容性不稳定的 HTML5 `dragstart/drop`。保存成功后列表与两类地图共同重绘。
- 桌面端行程节点头部保持把手、时间、类型和编辑操作单行对齐。拖拽把手命中区至少 44px，并禁止把手内部图标、图片和文字被浏览器选中或单独拖走；移动端继续使用既有指针阈值拖动。
- 行程日期导航以月日和星期为主信息，当日主题在日期导航下方单独显示，避免主题挤压日期识别。
- 每次切换行程日期后，选中按钮自动滚动到横向导航中央；首尾日期允许在可用范围内尽量居中，禁止把选中项留在视口外。
- 正式攻略的每个行程节点都必须显示明确的开始与结束时间。时间属于计划字段，可以根据路线节奏提出并在确认阶段修订；无可靠开放时间或交通时间时同时标记待复核，禁止交付仅有地点顺序的正式攻略。
- 地点列表保留名称、日期、类型和时间摘要；地址、备注及多个攻略链接放入单节点详情。链接支持小红书笔记、公众号、餐厅、购票和其他网页。
- 行程节点和住宿记录都提供独立链接字段并在详情中展示；链接可以与地点级多个攻略链接合并去重。
- 新增地点优先使用已配置地图连接器完成关键词搜索。连接器不可用时表单只要求地点名称、日期、明确起止时间、链接和备注，禁止要求用户手填经纬度；具体日期视图默认当前日期，全程总览要求用户选择旅行日期。无坐标地点不显示地图标记。
- “可缩放地图”模式支持拖动、加减按钮、桌面鼠标滚轮缩放和移动端双指缩放；绘制地图承担路线总览与节点点选，不伪装真实道路或比例尺。
- 记账结果区使用“个人汇总 / 结算建议”两个子 Tab。切换只改变结果视图，不修改账单、分摊与结算计算。
- 个人汇总必须区分“个人应摊”和“实际支付”，净额固定按“实际支付 − 个人应摊”计算；正数显示应收，负数显示应付。禁止把包含付款人自身应摊金额的整笔支付标成“垫付”。每日费用同时展示每位参与人的具体分摊金额，便于核对均摊与自定义分摊。
- 结算建议按币种独立计算，先合并全部账单净额，再按应付、应收金额从大到小匹配。生成前校验总应收等于总应付，出现未知同行人、分摊合计不一致或未能完全平账时停止给出建议并显示数据错误。页面需说明跨账单互欠已经抵销，避免将净额建议误读为单笔账单分摊。
- 记账弹窗选择“均摊”时隐藏自定义金额输入；选择“自定义”时显示各参与人金额与实时合计。单人金额不得大于账单总额，自定义合计必须等于账单总额。
- 记账模块不得展示退款与还款入口；首版只展示账单、个人汇总与结算建议。
- 航班卡片和交通编辑器支持航站楼、登机口、建议到达机场、值机截止、登机时间、起飞与到达时间。已预订航班按航班号和日期查询；未预订行程可按已确认的时间窗口推荐一趟真实可查航班，状态保持 `planned`，禁止把推荐航班标成已预订。
- 出行票据的“编辑信息”和“清空”按钮尺寸一致；“清空”移除该票据记录并保留已上传资料和附件。
- 待办使用可触控原生复选框，勾选成功后标题与说明划线，取消后恢复。每条有提醒日期的待办提供“添加到手机日历”；移动端优先调用系统分享／日历面板，桌面端再打开标准 ICS 文件。
- 单条提醒使用“添加到日历”，批量操作使用“导出日历文件”。浏览器支持文件分享时打开系统分享面板；移动端不支持时打开 ICS 文件，桌面端下载 ICS。页面不得承诺通用 Web 无法保证的静默写入系统日历。
- 交通票据和资料模块都展示附件能力状态。宿主提供可共享对象存储时开放上传入口，并在编辑器中为已保存记录提供上传按钮；能力缺失时显示“附件未启用”，禁止用只在本机可见的存储冒充共享附件。
- `aviation` 的五模块页面结构都以 `travel-prototype` 为视觉和信息层级基线：出行票面与右侧时间卡、行程中轴线节点与大幅绘制地图、准备双栏清单、记账每日费用与结果侧栏、资料分类列表。宿主不得把这些结构替换成通用卡片堆叠。
- 所有来源记录必须显示核验日期、时效类型、有效期和当前状态。上一年度或已过有效期的动态资料只能标记为“需要复核”，不得支撑当前事实结论。
- 宿主要求登录后编辑时，身份验证在打开新增、编辑或数据弹窗前完成。宿主适配器使用可选 `prepareEdit()`；登录弹窗使用原生 `<dialog>.showModal()` 或宿主等价顶层模态能力。发码、验证、失败、成功和取消路径都必须恢复按钮状态并结束等待，取消后页面与编辑入口保持可操作。
- 腾讯地图 MCP、WebService API 与 JavaScript API GL 分别承担 Agent 地点／路线数据、运行时地点接口和网页底图渲染。连接 MCP 不代表网页已经获得腾讯底图。腾讯底图上线前必须配置 Web 端 Key、精确域名白名单、官方 SDK、坐标转换和 `window.TRAVEL_MAP_ADAPTER`；缺少其中任一项时继续显示绘制地图或 OSM 保底，并明确提示尚未配置腾讯底图。

## 交付形态

每个正式部署都必须提供 `travel-app-manifest.json`，记录公开版本、数据 schema、宿主模式和部署标识。版本清单不得包含 Token、Key、Cookie、用户邮箱或数据库凭据。产品升级默认更新原站点并保留原数据、附件、权限、域名和访问链接；纯代码升级后 TravelPack 必须与升级前完全一致。

### 完整云端工具

完整工具必须同时具备：

- 官方五模块前端；
- 真实云端 TravelPack 读取与保存；
- 所有者编辑入口与只读分享入口；
- revision、宿主版本控制或保存前版本复查；
- 刷新后数据恢复；
- 只读写入拒绝；
- 附件仅在用户启用对应存储后开放。

宿主缺少其中任一项时，禁止把结果称为“完整产品”或“已完成上线”。

### UI 样式预览

运行：

```bash
node scripts/build_static_preview.mjs <travelpack.json> <output-directory> --ui-review
node scripts/serve_ui_preview.mjs <output-directory> --port 0
```

生成物沿用相同五模块 UI，并把 TravelPack 嵌入页面。第二条命令输出本地 HTTP URL，Agent 必须通过浏览器打开该 URL。禁止直接展示 `index.html` 文件或使用 `file://` 作为审核页，因为文件查看器无法可靠加载 ES Module、样式和依赖资源。

有效的 UI 审核必须同时满足：

1. 页面通过 HTTP(S) 打开，`body[data-app-ready="true"]` 已出现。
2. 真实旅行标题、日期、出行票面和五模块导航完成渲染。
3. 点击样式入口能够打开选择弹窗；至少切换两种风格，页面根节点的 `data-style` 同步变化。
4. 用户能够直接看到六种样式效果。宿主无法提供交互式本地预览时，改为提供六种真实浏览器截图；禁止只提供风格名称。

该形态只用于视觉确认，不保存编辑、不生成访问 Token、不承载附件。它不能作为用户要求上线时的最终交付。

## 部署后强制验收

打开真实线上地址后逐项验证：

1. 页面存在且仅存在五个一级模块入口：概览、行程、准备、记账、资料。地图与 AI Copilot 不得作为一级入口出现。
2. 页面加载的标题、日期和目的地来自本次 TravelPack。
3. 默认绘制地图在真实浏览器中显示路线、编号标记和可点击地点详情；切换网页底图后渲染出可辨识道路或地标、服务商归因、路线和编号标记，缩放、平移后内容更新。保留两种地图截图，禁止只检查瓦片 HTTP 状态码。
4. 五个模块逐一打开且无控制台异常。
5. 完整云端工具还需验证编辑保存、刷新恢复、只读拒写和旧版本冲突提示。标准云模式验证 HTTP 412；宿主原生模式验证等价冲突结果。
6. 线上页面如果只有一份长报告、没有五模块导航，立即判定交付失败并停止宣称完成。
7. 最终页面不得显示“演示只读”“静态只读预览”或“UI 样式预览”。
8. 用户指定微信或其他分享渠道时，使用该渠道实机打开并验证首页加载、五模块导航和只读数据。失败时记录具体拦截表现并说明可用替代入口，禁止把未经官方证实的原因写成平台白名单结论。
