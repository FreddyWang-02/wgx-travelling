# 规划智能：约束、偏好、候选池与可解释决策

本文件定义旅行规划阶段的智能规则，约束 [SKILL 工作流](../SKILL.md) 的研究到规划阶段。不修改 [TravelPack 1.1](travelpack-1.1.md) 字段契约，不引入 schema 变更。

## 意图、偏好与约束提取

1. 先提取意图，再提取偏好与约束。三类信息分开记录，禁止混写。
2. 偏好缺失时采用保守默认：不假设早起、不假设可承受高强度步行、不假设接受拥挤。默认节奏为每日 3 至 5 个节点，含休息与用餐。
3. 用户明确给出的事实原样保留；推断出的偏好必须标注"推断"，并在偏好摘要阶段让用户确认或修正。

## Hard Constraints（硬约束）

以下条目是 Hard Constraint：

- 航班：用户已确认或已购票的航班，包括日期、航班号、出发与到达时间。
- 酒店入住/退房：已预订住宿的 check-in 与 check-out 日期。
- 已预约餐厅：有确认凭据的固定用餐预约。
- 演出/活动：有日期与时间的票券项目。
- 必去地点：用户明确指定必须包含的地点与日期。
- 行动能力限制：用户声明的无障碍需求、体力限制或时间不可用。
- 用户明确指定不可修改的安排：用户原话标记为"必须"、"不能动"、"已定"的条目。

规则：

- Hard Constraint 不得被 AI 静默修改、移动、删除或覆盖。
- 规划与行程草案必须围绕 Hard Constraint 组织；冲突必须显式展示给用户并等待决定，禁止自动取舍。
- 修改 Hard Constraint 只来自用户明确指令，修改后以用户表述为准。
- Hard Constraint 在行程中的承载方式：航班写入 `transportSegments`，住宿写入 `stays`，预约餐厅、演出、必去地点与时间窗写入 `itineraryItems`，均保留用户给定的时间。

## Soft Preferences（软偏好）

以下条目是 Soft Preference：

- 不喜欢早起。
- 不喜欢赶。
- 少走路。
- 喜欢拍照。
- 喜欢咖啡馆。
- 避开人群。
- 预算倾向。
- 旅行节奏（宽松、均衡、充实）。
- 同类饮食、氛围、景观偏好。

规则：

- Soft Preference 用于候选排序与行程优化，允许在冲突时权衡，但权衡必须可解释。
- 多个 Soft Preference 冲突时按用户当次强调的优先；仍无法判断时给用户提供 1 到 2 个替代方案，不让用户做无上下文的选择题。
- 禁止把 Soft Preference 升级为 Hard Constraint；禁止因 Soft Preference 破坏 Hard Constraint。

## Research 到 Candidate Pool

研究结果不直接变成最终攻略，中间经过 Candidate Pool：

1. **候选地点（Candidate Places）**：每个候选保存名称、来源链接、所属区域、开放时间或动态状态、是否满足用户兴趣主题。候选不足时扩大搜索，禁止用低置信来源补齐。
2. **地理聚类（Geographic Clustering）**：按区域或街区分组候选；无坐标时按官方地址与地图空间关系分组，不确定时标记"分区待核验"。
3. **时间可行性（Time Feasibility）**：按真实开放时间、交通时间与用餐时间判断同天可容纳的候选数量；不满足的候选降级为备选或移至其他天。
4. **约束检查（Constraint Check）**：逐一校验 Hard Constraint 不被破坏；与 Soft Preference 冲突的记录冲突与取舍理由。
5. **偏好匹配（Preference Matching）**：按 Soft Preference 对通过检查的候选排序，输出前 3 名与备选。
6. **最终行程（Final Itinerary）**：仅用户确认路线后，才把胜出候选转为正式 `itineraryItems`，每个节点补齐明确的 `startTime` 与 `endTime`。

候选池在会话中以区域摘要形式展示：每个区域列出胜出候选、落选原因（可选）与备选，等待用户确认路线。用户确认前的候选不构成正式行程，不得写入 TravelPack。

## 约束感知规划

行程规划按以下优先级组织每日安排：

1. 地理聚类：同日节点尽量落在相邻区域，减少跨区移动。
2. 真实交通时间：使用地图路线数据或官方交通时间；无法取得时标记待核验，禁止虚构精确时长。
3. 用户节奏：按 Soft Preference 中的节奏与"不喜欢赶"等限制控制节点密度与移动距离。
4. 每日合理密度：默认 3 至 5 个节点，包含用餐与休息时间。
5. 用餐时间：按目的地的常规用餐时段预留，餐厅预约优先于自由用餐。
6. 休息时间：上午、下午各保留 30 至 60 分钟缓冲，或把长移动放在一天内移动最少的位置。
7. Hard Constraints：任何节点安排不得与 Hard Constraint 冲突；冲突必须显式上报。
8. Soft Preferences：在 1 至 7 项满足的前提下排序取舍。

## 可解释规划

1. 每个进入最终行程的关键决策生成一句简短 planning reason，使用用户可理解的自然语言。
2. planning reason 只写结论与依据，例如：
   - "浅草和上野安排在同一天，因为位于相邻区域，可以减少跨区移动。"
   - "保留 19:30 的餐厅预约，因此下午行程提前结束。"
3. 禁止保存或展示模型隐藏推理过程或 chain-of-thought；planning reason 是面向用户的结论摘要，不是推理日志。
4. planning reason 展示在逐日草案与用户确认阶段；用户确认后随行程备注保存（复用 TravelPack 1.1 的 `itineraryItems[].notes` 或 `materials` 攻略类条目），不新增 schema 字段。
5. 后续 TravelPack 1.2 将增加 `decisionLog`；Phase 1 只定义上述行为与数据需求，不修改 `schemaVersion`。

## 缺失信息检查

规划前检查以下信息，缺失时向用户提问或标记"待确认"：

- 目的地、日期、同行人、节奏、预算倾向。
- 已知 Hard Constraint 的完整时间（航班与预约的日期、时刻）。
- 行动能力限制与饮食禁忌。
- 已预订项目的确认凭据或订单号（用于写入 `materials`）。

缺少 Hard Constraint 的时间时不得默认填写，使用 `null` 或 `precision = "date"` 表达已知粒度。
